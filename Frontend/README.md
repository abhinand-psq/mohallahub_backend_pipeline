# Mohalla Frontend --- Dockerization Documentation

## 1. Overview

The Mohalla frontend is a React application built with Vite. It is
containerized using a **two-stage Docker build**.

The design separates:

1.  **Build stage** --- installs Node.js dependencies, receives the
    environment-specific frontend configuration, and creates the
    production Vite build.
2.  **Runtime stage** --- uses an unprivileged Nginx image to serve the
    generated static files.

This keeps the final runtime image focused on serving the compiled
frontend instead of carrying the Node.js build environment.

Docker recommends multi-stage builds because build-time dependencies can
be kept out of the final runtime image.

## 3. Stage 1 --- React Build

The first stage uses:

``` dockerfile
FROM node:20-alpine AS builder
```

This stage provides the Node.js environment required to install
dependencies and build the React application.

### Dependency installation

The package files are copied before the application source:

``` dockerfile
COPY package*.json ./
RUN npm ci
```

This ordering is intentional. Dependency installation can be reused
through Docker's build cache when the package files have not changed.

### Application source

The application source is then copied:

``` dockerfile
COPY . .
```

### Build-time environment values

The frontend accepts two build arguments:

``` dockerfile
ARG VITE_ENV
ARG VITE_BACKEND_API_URL
```

They are then made available to the Vite build:

``` dockerfile
ENV VITE_ENV=${VITE_ENV}
ENV VITE_BACKEND_API_URL=${VITE_BACKEND_API_URL}
```

The production frontend is generated by:

``` dockerfile
RUN npm run build
```

The important point is that these Vite values are **build-time
configuration**. Vite statically exposes `VITE_*` variables to the
client bundle when the application is built. Therefore, changing the
backend URL requires building the frontend image again with the new
value.

Example:

``` bash
docker build \
  --build-arg VITE_ENV=production \
  --build-arg VITE_BACKEND_API_URL=https://api.example.com \
  -t mohalla-frontend:1.0 .
```

In the project pipeline, these values can be supplied by Jenkins during
the Docker build.

## 4. Stage 2 --- Nginx Runtime

The second stage uses:

``` dockerfile
FROM nginxinc/nginx-unprivileged:alpine
```

Instead of running Node.js in production, the compiled files from
`/app/dist` are served by Nginx:

``` dockerfile
COPY --from=builder /app/dist /usr/share/nginx/html
```

Only the production build is copied from the builder stage.

This means the final image does not need the complete Node.js
development/build environment.

## 5. Nginx Configuration

The project uses a custom `nginx.conf`:

``` nginx
server {
    listen 8080;

    server_name _;

    root /usr/share/nginx/html;

    index index.html;

    location / {
        try_files $uri $uri/ /index.html;
    }
}
```

The configuration is copied into the image with:

``` dockerfile
COPY nginx.conf /etc/nginx/conf.d/default.conf
```

### Why port 8080?

The image uses the unprivileged Nginx image, so Nginx listens on:

``` text
8080
```

The Dockerfile documents this with:

``` dockerfile
EXPOSE 8080
```

Kubernetes can then expose the container through a Service and/or
Ingress.

## 6. Why `try_files` is required

Mohalla is a React Single Page Application (SPA).

For example, the browser may request:

``` text
/
```

and React can then handle client-side routes such as:

``` text
/dashboard
/profile
/tasks
```

These routes are not necessarily physical files inside
`/usr/share/nginx/html`.

The configuration:

``` nginx
try_files $uri $uri/ /index.html;
```

tells Nginx to:

1.  Check whether the requested file exists.
2.  Check whether the requested directory exists.
3.  If neither exists, return `/index.html`.

The request therefore reaches the React application, which can handle
the client-side route.

Without this fallback, directly refreshing a React route can result in
an Nginx `404`.

## 8. Main Benefits

### Smaller runtime responsibility

Node.js is required to build the application but is not required to
serve the already-built static files.

### Separation of build and runtime

The build environment and production-serving environment are separated.

### Better layer caching

`package*.json` is copied before the application source, allowing the
dependency-installation layer to be reused when only source code
changes.

### SPA routing support

The Nginx `try_files` fallback makes client-side React routes work
correctly.

### Non-root runtime

The project uses `nginxinc/nginx-unprivileged:alpine`, allowing the web
server to run as an unprivileged user.
